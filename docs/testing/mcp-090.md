# MCP and BitTorrent validation, 24 October 2026

## Checks

The final full suite passed 1,010 tests with 61 optional tests skipped. Separately, the opt-in browser flow passed, all nine live Classic tests passed, and the packaged MCP bridge passed its smoke check. Ruff and mypy passed. Both review axes have no remaining findings after the reported fixes.

## MCP

The public MCP endpoint was tested over HTTP with separate agent tokens and owner approval. Tests used temporary application state and an in-memory copy of settings. Saved desktop settings and the user's original download queue were not changed.

A real Plan selected three c411 ebooks totaling 20,643,093 bytes. MCP queued and sent them to qBittorrent after owner approval. All three reached 100% and remain available for seeding.

The same files were used to exercise discovery, capability resources, overview, client refresh, paginated lists, search options, search, torrent details, saved goals, goal status, goal Plans, queue listing, pause, resume and recheck. A file was removed from the client with its data retained, then successfully Reseeded through MCP and the normal Verification workflow.

Deletion was tested on a separate, generated disposable torrent and file. Owner review identified the target before approval; the job and its file were then removed. Cancellation and token revocation were tested. Cross-connection access to jobs was refused.

Upload preview and description edits used a real local ebook. Draft creation and Upload seeding were tested through MCP with a simulated c411 service and generated STL fixture, avoiding a duplicate public upload. Live c411 Draft creation was not tested.

Regression tests cover proposal-only defaults, authentication, allowed clients, budgets, incomplete downloads sharing a disk, stable request IDs, removal review, client switching and settings isolation. Disabling access cancels jobs even when their proposals are outside the 100-entry display page. A failed MCP bind does not block ordinary desktop settings.

The Linux desktop package was built with PyInstaller. Its stdio bridge passed initialization, tool discovery and authenticated overview against an isolated HTTP server. Windows packaging has not been run locally.

## BitTorrent Classic

BitTorrent Classic 7.11.0.47391 was downloaded from the official site and extracted into a temporary Wine environment. Its test instance had independent settings and disposable files.

Nine live tests passed: single-file and multifile downloads, listing, file priorities, pause/resume/recheck, removal retaining data, full Reseeds, confirmed disk renames, Upload seeding and rejection of incorrect file content. The same adapter remains available for µTorrent Classic. Public setup API tests cover selecting BitTorrent, folder discovery, saved credentials and reconnecting.

## BitTorrent Web investigation

The official BitTorrent Web 1.6.0.6445 installer contains a Web UI bundle with its connection implementation. In a temporary Wine instance, local-token authentication and list/settings/version calls worked on port 38565. The protocol has a separate pending-torrent commit operation and different remove commands.

Uploading a generated fixture returned HTTP 200 with a build number but no observable torrent or pending torrent, even after polling and attempting the documented frontend commit flow. Therefore Web is not offered as a working client. This result does not establish that integration is impossible on Windows; a Windows add/commit/verify test is still needed before enabling downloads or Reseeds.
