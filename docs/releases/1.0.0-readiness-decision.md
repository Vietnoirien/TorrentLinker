# TorrentLinker 1.0.0 readiness decision

Status: accepted by the user on 2026-10-26.

## Decision

TorrentLinker 1.0.0 will prioritize reliability, clarity and complete workflows over
another major feature expansion. Users should be able to trust the application with
their files, Torrent Clients and queues without understanding its implementation.

The current feature scope, including RSS and Upload presentation improvements,
provides the foundation. Stabilization will turn these capabilities into predictable
workflows, especially when operations fail or are interrupted.

These are readiness criteria, not a claim that the current application meets them.
This decision sets no release date and does not authorize publication or a version
bump. Detailed stabilization planning follows the beta publication, as recorded in
[the beta decision](beta-and-stabilization.md).

## Required product promises

| Promise | Required evidence |
| --- | --- |
| Files remain safe | Reseeds preserve source data. Any supported disk rename follows the existing explicit per-torrent approval and recovery rules. Destructive operations are explicit. Retries and crashes do not silently repeat consequential actions. |
| Users know what will happen | Upload previews represent the submitted presentation. Download previews identify the exact release, Torrent Client and Download Folder. Adding to the app queue is clearly distinct from starting a download. |
| Work survives interruptions | Local Drafts, saved selections and queues survive restarts. Interrupted jobs recover predictably. Uncertain remote outcomes are reconciled before retrying. |
| Core workflows are complete | Library → Match → Verification → Reseed; files → Local Draft → review → Upload; and search/feed → selection → queue → download work end to end. Zen planning produces useful results or an actionable explanation of the blocking condition. |
| Interfaces agree | Desktop, web and MCP use the same validation and permission rules and provide essential workflow capabilities. Errors explain the problem and a useful next action. |
| Upgrades are dependable | Supported public compatibility contracts are documented. Migrations and backup/recovery procedures are tested. Releases continue to follow SemVer. |

File-safety criteria preserve the explicit µTorrent Classic and BitTorrent Classic
exceptions in [ADR-0013](../adr/0013-confirmed-disk-renames-for-utorrent.md); they do
not silently change those approved workflows.

## Assistant readiness

The assistant improves core workflows but is not required to complete them. It must:

- Retain and refine saved selections accurately across turns.
- Respect the chosen Torrent Client, Download Folder and operation scope.
- Recover from tool errors without bypassing validation or repeating uncertain
  consequential actions.
- Distinguish verified facts, unknown information and model guesses.
- Degrade usefully when a model lacks a capability. A weaker model reduces
  convenience, not safeguards enforced by the application.

## Supportability

Supportability is part of the 1.0 product, including connection diagnostics,
storage/path checks, clear job history and an exportable diagnostic report that
redacts credentials. Users and maintainers should be able to investigate ordinary
setup and operation failures without exposing secrets or reconstructing events from
chat messages.

## Evidence required before release

- No unresolved known bugs causing data loss, unintended downloads or duplicate
  submissions.
- Successful upgrade and restart tests across the supported deployment
  configurations.
- Real users completing the core workflows on Windows, Linux and Docker.
- A defined support matrix for Torrent Clients and model providers, distinguishing
  tested support from unverified compatibility.
- No recurring critical failures across consecutive beta releases, supported by
  test results and user reports from a sustained beta period.

The stabilization plan will define the concrete test matrix, severity criteria and
observation period. No arbitrary beta duration or release count is fixed here.

## Versioning and release path

On 2026-10-26, the user selected `1.0.0-beta.1` as the next publication and the
baseline for polish and stabilization, including the integrated Media Center.
This supersedes the earlier `0.13.0` prerelease target. It does not declare stable
1.0 readiness or waive any criteria above. Continue with `1.0.0-beta.N` during
stabilization; use a release candidate only when the remaining release blockers
are understood, then publish stable `1.0.0` when its evidence is complete.

Continue to follow SemVer. Public beta and release-candidate labels describe release
maturity; they do not replace compatibility-based versioning. A stable `0.x`
release does not itself establish 1.0 readiness. Declare `1.0.0` when the supported
public contracts and the operational evidence above are ready to be maintained.

Before that point, finish the currently authorized work, perform final publication
tests, publish the beta when requested, then plan and execute stabilization with
the user. Reserve release-candidate labels for a particular version believed ready,
with only final release blockers under evaluation.
