# Web and Docker support for 0.7.0

Approved direction, 24 October 2026: support NAS/home servers and hosted seedboxes from the first web release. Keep the desktop application. One owner and one selected Torrent Client per server; simultaneous browser sessions share that workspace.

## User workflows

- A first-run wizard tests a Torrent Client before saving it, retrieves available folder settings, checks filesystem access, suggests mappings, and tests the c411 key. Each step remains independently editable. API-only users can skip storage and c411 setup and manage torrents immediately.
- The backend reaches the Torrent Client. The browser never receives client credentials or c411 keys. The folder picker browses approved server storage roots, not the browser device.
- Existing client adapters serve qBittorrent, Deluge, Transmission and µTorrent. Preserve the meaning of removal versus deletion and protect torrents undergoing Verification.
- Support Torrents, Zen estimates/profile, Search with category options, the persistent Download Queue, Library Scan and Candidate comparison, Reseeds, catalogue refresh and planning, and Upload preparation/Drafts using existing domain functions.
- A closed browser does not stop jobs. Record progress, completion and failures. Server interruption must be visible and must not automatically replay uncertain mutations. Resume monitoring persisted Reseed Verification.
- Translate application paths through existing Path Mappings. An inaccessible remote path must not count as an empty directory, and the planner must not use container capacity for remote storage. Require accessible, verified storage for sends and planning when the API cannot establish those facts.
- Basic settings stay visible. Proxy configuration and provider-specific options are advanced. Include system/light/dark themes and a small-screen layout.

## Deployment

One headless process serves the UI, authenticated API and job worker. Package an image without Qt, run without root, persist configuration, credentials and jobs, and document both API-only seedbox and mounted-storage deployments. Desktop credentials continue using the operating system keyring; server credentials use an explicit server store or deployment secret files.

## Scope boundaries

The first web interface reuses domain workflows, not every desktop editor and preview. Archive extraction and µTorrent disk renames continue through the desktop's existing per-torrent confirmation flow. The web Upload editor supports category rules, files, NFO, description and hosted image URLs; the desktop 3D renderer remains available there. Description image hosts open as links in the web preview. Do not expose the ebook easter egg in release material.

No automatic SSH/SFTP mounts, multi-user isolation, simultaneous multi-client management or automatic release publication is part of this work.

## Agreed test boundaries

The user approved setup API tests, job API tests and browser setup/management flows. Review against starting commit `759d7a7fa24193d5a7699207979084c5f3365b8f`. Tests use fake clients and temporary storage; Docker checks do not use real credentials or media.
